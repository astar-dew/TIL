## 학습 목적

복잡도는 코딩테스트용 지식으로 배우는 경우가 많지만, 실제로는 **매일 하는 선택의 판단 기준**이다.

- 리스트에서 `in`으로 찾을까, `set`으로 바꿀까
- 반복문 안에서 DB를 조회해도 될까
- 인덱스를 걸면 왜 빨라지나
- 지금 잘 도는 코드가 데이터가 100배가 되어도 버틸까

이 글에서는 빅오 표기법과 계산 규칙을 정리한 뒤, **실무에서 복잡도가 실제로 문제되는 지점**을 정리한다. 후자에 비중을 둔다.

## 왜 초 단위로 재지 않는가

"이 함수는 0.3초 걸린다"는 측정은 하드웨어, 언어, 부하 상태에 따라 달라진다. 알고리즘 자체의 성질을 말하려면 **입력이 커질 때 연산 횟수가 어떤 비율로 늘어나는지**를 봐야 한다.

```text
입력이 2배가 되면 시간은 몇 배가 되는가?

O(n)      → 2배
O(n log n) → 2배 조금 넘게
O(n²)     → 4배
O(2ⁿ)     → 제곱
```

**복잡도는 절대 속도가 아니라 증가율을 말한다.** 이 구분이 핵심이다.

## 빅오 표기법

입력 크기 `n`이 충분히 클 때의 **상한**을 나타낸다. 규칙은 두 가지다.

```text
T(n) = 3n² + 100n + 5000
       ↓ 최고차항만 남기고
     = n²
       ↓ 상수 계수 제거
O(n²)
```

1. **최고차항만 남긴다** — `n`이 커지면 낮은 차수는 무시할 수준이 된다
2. **상수 계수를 버린다** — `3n²`이든 `100n²`이든 증가 패턴은 같다

### 상수를 무시하면 안 될 때

이론적 전제이지 실무 전제는 아니다. 다음 경우에는 상수가 지배한다.

- **`n`이 작을 때** — `n=10`에서는 `O(n²)`가 `O(n log n)`보다 빠를 수 있다. Python `sorted()`가 작은 배열에 삽입 정렬을 쓰는 이유다
- **상수가 엄청 클 때** — `O(n)`이지만 매 반복마다 네트워크 요청을 한다면, `O(n²)`짜리 메모리 연산보다 훨씬 느리다

이 두 번째가 실무에서 훨씬 자주 문제된다. 뒤에서 다룬다.

## 자주 나오는 복잡도

| 복잡도 | 이름 | 예시 |
| --- | --- | --- |
| `O(1)` | 상수 | 배열 인덱스 접근, 해시 조회, 딕셔너리 `get` |
| `O(log n)` | 로그 | 이진 탐색, 균형 트리 탐색, DB B-tree 인덱스 |
| `O(n)` | 선형 | 리스트 전체 순회, `in` 연산, 최댓값 찾기 |
| `O(n log n)` | 선형 로그 | 병합·퀵·힙 정렬. **비교 기반 정렬의 하한** |
| `O(n²)` | 이차 | 이중 반복문, 버블 정렬 |
| `O(2ⁿ)` | 지수 | 부분집합 전체 탐색, 메모이제이션 없는 피보나치 |
| `O(n!)` | 팩토리얼 | 순열 전체 탐색, 외판원 문제 완전 탐색 |

### 숫자로 보는 감각

대략 **1초에 1억 번** 연산한다고 가정하면 이렇게 된다.

| n | `O(n)` | `O(n log n)` | `O(n²)` | `O(2ⁿ)` |
| --- | --- | --- | --- | --- |
| 10 | 10 | 33 | 100 | 1,024 |
| 1,000 | 1천 | 약 1만 | 100만 | 사실상 불가능 |
| 100,000 | 10만 | 약 170만 | **100억 (100초+)** | 불가능 |
| 1,000,000 | 100만 | 약 2천만 | 불가능 | 불가능 |

**`O(n²)`는 `n`이 10만만 되어도 실용 범위를 벗어난다.** 반면 `O(n log n)`은 100만에서도 버틴다. 이 경계 감각이 실무에서 유용하다.

## 계산 규칙

### 순차 실행은 더한다 → 큰 쪽만 남는다

```python
def process(items):
    for item in items:        # O(n)
        validate(item)

    items.sort()              # O(n log n)

    for item in items:        # O(n)
        save(item)
# O(n) + O(n log n) + O(n) = O(n log n)
```

### 중첩 반복문은 곱한다

```python
for a in list_a:              # n번
    for b in list_b:          # m번
        compare(a, b)
# O(n × m), 두 리스트 크기가 같다면 O(n²)
```

### 절반씩 줄면 로그

```python
def binary_search(arr, target):
    lo, hi = 0, len(arr) - 1
    while lo <= hi:               # 매 반복마다 범위가 절반
        mid = (lo + hi) // 2
        if arr[mid] == target:
            return mid
        if arr[mid] < target:
            lo = mid + 1
        else:
            hi = mid - 1
    return -1
# O(log n)
```

`n`이 100만이어도 20번이면 끝난다.

### 재귀는 호출 횟수 × 호출당 작업량

```python
def fib(n):                      # 호출마다 2번씩 분기
    if n <= 1:
        return n
    return fib(n - 1) + fib(n - 2)
# O(2ⁿ) — n=40이면 이미 버겁다

def fib_memo(n, cache={}):       # 각 n을 한 번만 계산
    if n <= 1:
        return n
    if n not in cache:
        cache[n] = fib_memo(n - 1) + fib_memo(n - 2)
    return cache[n]
# O(n)
```

메모이제이션 하나로 `O(2ⁿ)`이 `O(n)`이 된다. 동적 계획법의 출발점이다.

## 공간 복잡도

추가로 쓰는 메모리를 본다. 보통 **입력 자체는 제외**하고 계산한다.

```python
def sum_all(nums):
    total = 0                 # 변수 하나
    for n in nums:
        total += n
    return total
# 공간 O(1)

def double_all(nums):
    return [n * 2 for n in nums]   # 입력 크기만큼 새 리스트
# 공간 O(n)
```

**재귀는 호출 스택도 메모리다.** 이 점을 자주 놓친다.

```python
def countdown(n):
    if n == 0:
        return
    countdown(n - 1)
# 공간 O(n) — 스택 프레임이 n개 쌓인다
```

Python의 기본 재귀 한도는 1000 근처라, 깊은 재귀는 `RecursionError`로 터진다. 스택 프레임이 스레드마다 별도로 잡힌다는 점은 [프로세스와 스레드의 차이](../../cs/2026-08-03-process-thread-memory.md)에 정리했다.

시간과 공간은 대체로 **맞바꾸는 관계**다. 메모이제이션은 메모리를 써서 시간을 줄이는 전형적인 거래다.

## 최선·평균·최악

| 자료구조/알고리즘 | 평균 | 최악 | 최악이 언제 |
| --- | --- | --- | --- |
| 해시 테이블 조회 | `O(1)` | `O(n)` | 해시 충돌이 몰릴 때 |
| 퀵 정렬 | `O(n log n)` | `O(n²)` | 피벗이 계속 최솟값/최댓값일 때 |
| 이진 탐색 트리 | `O(log n)` | `O(n)` | 한쪽으로 치우쳐 리스트가 될 때 |

**보통 최악을 기준으로 판단한다.** 평균만 보고 설계하면 특정 입력에서 서비스가 멈출 수 있고, 이 성질이 공격에 이용되기도 한다(해시 충돌 공격).

## 상각 분석

가끔 비싼 연산이 있어도, **여러 번에 나눠 보면 평균이 싼** 경우가 있다.

```python
items = []
for i in range(1_000_000):
    items.append(i)     # 평균 O(1)
```

동적 배열은 공간이 차면 더 큰 배열을 새로 만들어 복사한다. 그 순간은 `O(n)`이다. 하지만 용량을 **배로** 늘리기 때문에 복사가 드물게 일어나고, 전체를 평균 내면 연산당 `O(1)`이 된다. 이를 상각 상수 시간이라 한다.

## 실무에서 복잡도가 실제로 문제되는 지점

여기가 이 글의 핵심이다. 실무에서 성능을 망치는 것은 대개 정렬 알고리즘 선택이 아니라 **아래 패턴들**이다.

### 1. 반복문 안의 DB 조회 (N+1)

```python
# O(n)번의 네트워크 왕복 — 상수가 거대하다
orders = Order.objects.all()          # 쿼리 1번
for order in orders:
    print(order.user.name)            # 주문마다 쿼리 1번 추가
```

```python
# 쿼리 1~2번
orders = Order.objects.select_related("user").all()
```

연산 횟수로는 둘 다 `O(n)`이지만 **한 번의 비용이 수만 배 차이 난다.** 메모리 접근은 나노초, DB 왕복은 밀리초 단위다.

> **`O(n)`이라도 그 `n`이 네트워크 왕복이면 다르다.** 복잡도를 볼 때 "한 번의 비용"을 함께 봐야 하는 이유다.

자세한 내용은 [Django ORM과 DRF의 N+1 문제 최적화](../../web/backend/2026-07-20-django-drf-internals-and-tradeoffs.md)에 정리했다.

### 2. 인덱스가 하는 일이 바로 이것

```sql
SELECT * FROM users WHERE email = 'a@example.com';
```

| 상황 | 복잡도 | 100만 행에서 |
| --- | --- | --- |
| 인덱스 없음 (풀 스캔) | `O(n)` | 100만 행 확인 |
| B-tree 인덱스 | `O(log n)` | 약 20번 탐색 |

인덱스는 정렬된 트리를 미리 만들어 두고 이진 탐색과 같은 방식으로 찾는 구조다. **"인덱스를 걸면 빨라진다"의 실체가 `O(n)` → `O(log n)`** 이다.

동시에 인덱스의 비용도 설명된다. 쓰기마다 트리를 갱신해야 하므로 `INSERT`/`UPDATE`가 느려진다. 읽기를 위해 쓰기를 내주는 거래다.

### 3. 자료구조 선택 — 가장 흔하고 가장 쉬운 개선

```python
# O(n × m) — 리스트의 in은 전체를 훑는다
blocked = ["user1", "user2", ...]          # 10,000개
for user in users:                          # 10,000명
    if user.id in blocked:                  # 각각 10,000번 비교
        continue
# 총 1억 번 비교
```

```python
# O(n) — set의 in은 해시 조회
blocked = {"user1", "user2", ...}           # 중괄호로 바꾸기만
for user in users:
    if user.id in blocked:                  # O(1)
        continue
# 총 10,000번
```

**괄호 하나 바꿔서 1억 번이 1만 번이 된다.** 실무에서 가장 자주 마주치는 개선이고, 코드 리뷰에서 봐야 할 1순위다.

| 연산 | list | set / dict |
| --- | --- | --- |
| `in` (포함 확인) | `O(n)` | `O(1)` |
| 인덱스 접근 | `O(1)` | 불가 |
| 순서 유지 | 유지 | dict는 삽입 순서 유지 |
| 맨 앞 삽입/삭제 | `O(n)` | — |

맨 앞에서 자주 넣고 빼야 한다면 `collections.deque`를 쓴다. `list.pop(0)`은 `O(n)`이다.

### 4. 문자열 누적

```python
# O(n²) — 매번 새 문자열을 만든다
result = ""
for line in lines:
    result += line

# O(n)
result = "".join(lines)
```

문자열은 불변이라 `+=`마다 전체를 복사한다.

### 5. 정렬 후 탐색이 이득인 시점

한 번 찾을 거면 그냥 선형 탐색(`O(n)`)이 낫다. **여러 번 찾을 거면** 정렬(`O(n log n)`) 후 이진 탐색(`O(log n)`)이 이득이다.

```text
k번 탐색할 때
  선형:   O(k × n)
  정렬+이진: O(n log n + k log n)

k가 커질수록 후자가 유리
```

DB 인덱스가 정확히 이 거래다. 한 번 만들어 두고 계속 이득을 본다.

## 복잡도만으로 판단하면 안 되는 경우

| 상황 | 이유 |
| --- | --- |
| `n`이 항상 작다 | 상수가 지배한다. 가독성을 택하는 게 낫다 |
| 병목이 I/O다 | 알고리즘을 고쳐도 DB·네트워크가 병목이면 소용없다 |
| 캐시 지역성 차이 | 배열이 연결 리스트보다 실측이 빠른 경우가 많다 |
| 메모리 한계 | 시간을 줄이려다 OOM이 날 수 있다 |

**결국 측정해야 한다.** 복잡도는 "어디를 의심할지" 알려주는 지도이지 측정의 대체물이 아니다.

```python
import cProfile
cProfile.run("main()")     # 실제 병목 확인
```

## 자주 하는 실수

### 반복문이 하나면 `O(n)`이라고 단정

반복문 안에서 `list.index()`나 `in`을 쓰면 그 자체가 `O(n)`이라 전체는 `O(n²)`다.

### 내장 함수는 공짜라고 생각

`sorted()`는 `O(n log n)`, `max()`는 `O(n)`, `list.insert(0, x)`는 `O(n)`이다. 반복문 안에 있으면 곱해진다.

### 상수를 항상 무시

네트워크 왕복이 상수라면 무시하면 안 된다. N+1이 정확히 이 경우다.

### 재귀의 공간 복잡도를 빼먹음

호출 스택도 메모리다.

### 평균만 보고 설계

해시 테이블 최악은 `O(n)`이다. 외부 입력이 키가 되는 경우 특히 주의한다.

### 복잡도만 개선하고 측정 안 함

실제 병목이 DB였다면 아무 변화가 없다.

## 정리

- 복잡도는 절대 속도가 아니라 **입력이 커질 때의 증가율**을 나타낸다.
- 빅오는 최고차항만 남기고 상수를 버리지만, `n`이 작거나 상수가 거대하면 그 전제가 깨진다.
- `O(n²)`는 `n`이 10만이면 실용 범위를 벗어나고, `O(n log n)`은 100만에서도 버틴다.
- 공간 복잡도에는 재귀 호출 스택이 포함된다.
- 보통 최악을 기준으로 판단한다. 해시 조회의 최악은 `O(n)`이다.
- 실무에서 문제되는 것은 대개 정렬 선택이 아니라 **반복문 안의 DB 조회, 리스트 `in`, 문자열 누적**이다.
- 인덱스는 `O(n)` 풀 스캔을 `O(log n)`으로 바꾸는 대신 쓰기 비용을 늘리는 거래다.
- 복잡도는 어디를 의심할지 알려주는 지도이고, 최종 판단은 측정으로 한다.
