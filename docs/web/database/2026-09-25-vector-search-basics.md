## 학습 목적

RAG나 추천을 만들 때 "벡터 DB를 쓴다"는 말은 쉽게 나오지만,
**그것이 관계형 DB와 무엇이 다르고 무엇을 포기하는 것인지**는 잘 정리되지 않는다.

이 글이 답하는 질문은 셋이다.

- 왜 키워드가 아니라 벡터로 검색하는가
- **벡터 검색은 왜 "정확한 답"을 포기하는가**
- 그래서 관계형 DB를 쓰던 감각이 어디서 깨지는가

제품 비교가 아니라 **원리와 트레이드오프**를 다룬다.

## 왜 벡터로 검색하는가

키워드 검색은 **글자가 겹쳐야** 찾는다.

```text
질문: "노트북이 안 켜져요"

문서 A: "랩톱 전원이 들어오지 않을 때"   → 키워드 0개 일치. 못 찾는다
문서 B: "노트북 케이스 추천"             → "노트북" 일치. 찾는다
```

**의미는 A가 맞는데 글자는 B가 맞다.** 동의어 사전을 쌓아 올리는 방식으로는 한계가 분명하다.

벡터 검색은 문장을 **좌표**로 바꿔 놓고 **거리**로 찾는다.
"노트북이 안 켜져요"와 "랩톱 전원이 들어오지 않을 때"가 가까운 좌표에 놓이면, 글자가 겹치지 않아도 찾힌다.

## 임베딩 — 의미를 좌표로 바꾸기

**임베딩 모델**이 텍스트를 고정 길이의 실수 벡터로 바꾼다.

```text
"노트북이 안 켜져요"  →  [0.021, -0.113, 0.077, … ]   1536개의 숫자
"랩톱 전원이 안 들어와" →  [0.019, -0.108, 0.081, … ]   ← 가깝다
"오늘 점심 뭐 먹지"     →  [-0.203, 0.451, -0.012, … ]  ← 멀다
```

차원 수는 모델이 정한다. 예를 들어 OpenAI의 `text-embedding-3-small`은 1536차원,
`text-embedding-3-large`는 3072차원이다. **차원이 높을수록 표현력은 늘지만 저장 비용과 계산량도 같이 는다.**

여기서 실무에 바로 걸리는 제약이 둘 있다.

**① 같은 모델로 만든 벡터끼리만 비교할 수 있다.**
모델이 다르면 좌표계 자체가 다르다. A 모델의 `[0.02, -0.11, …]`과 B 모델의 같은 숫자는 아무 관계가 없다.

**② 모델을 바꾸면 전체를 다시 계산해야 한다.**
임베딩 모델 교체는 **전면 재색인**이다. 문서가 수백만 건이면 비용과 시간이 그대로 든다.
"나중에 더 좋은 모델로 갈아타지" 라고 가볍게 미룰 결정이 아니다.

## 얼마나 가까운가 — 유사도 척도

세 가지가 주로 쓰인다.

| 척도 | 무엇을 보나 | 범위 |
| --- | --- | --- |
| **코사인 유사도** | 두 벡터가 이루는 **각도**. 크기는 무시 | -1 ~ 1 (클수록 유사) |
| **내적(dot product)** | 각도 + **크기** | 제한 없음 |
| **유클리드 거리(L2)** | 두 점 사이의 **직선 거리** | 0 이상 (작을수록 유사) |

```text
코사인은 방향만 본다

    ↗ A          A와 B는 길이가 달라도
   ↗             각도가 같으면 코사인 유사도 = 1
  ↗↗ B
```

**대부분의 임베딩 모델은 벡터를 정규화해서(길이를 1로) 내보낸다.** 그러면 재미있는 일이 생긴다.

> 길이가 1인 벡터끼리는 **코사인 유사도와 내적이 같은 값**이 되고,
> 유클리드 거리도 코사인과 단조 관계가 된다. 즉 **셋 중 무엇을 써도 순위가 같다.**

그래서 실무에서는 계산이 가장 싼 **내적**을 쓰는 경우가 많다.

**중요한 것은 모델이 권장하는 척도를 따르는 것이다.** 모델은 특정 척도를 전제로 학습된다.
권장 척도와 다른 것을 쓰면 순위가 미묘하게 어긋나고, **에러가 아니라 품질 저하로 나타나서** 알아채기 어렵다.

## 완전 탐색의 비용과 ANN의 등장

가장 정확한 방법은 **전부 비교하는 것**이다.

```text
질의 벡터 1개  vs  저장된 벡터 N개
각 비교마다 D차원을 곱하고 더한다

계산량 = O(N × D)
```

[시간 복잡도](../../algorithm/concepts/2026-08-17-time-space-complexity.md) 관점에서 보면
**N에 선형으로 비례한다.** 문서가 10배 늘면 검색도 10배 느려진다.

```text
N = 1,000       × 1536차원  →  즉시
N = 1,000,000   × 1536차원  →  약 15억 번의 곱셈. 질의 하나마다
```

관계형 DB라면 인덱스를 걸어 해결할 자리다. 그런데 **B-Tree는 여기서 쓸 수 없다.**
B-Tree는 "정렬 가능한 하나의 축"을 전제하는데, 1536차원 공간에는 그런 축이 없다.

그래서 벡터 검색은 다른 선택을 한다.

> **정확한 최근접 이웃을 포기하고, 근사한 답을 빠르게 얻는다.**
> 이것이 **ANN**(Approximate Nearest Neighbor)이고, 벡터 DB의 핵심 거래다.

### 얼마나 포기하는가 — recall

근사의 품질은 **recall**로 잰다.

```text
recall@10 = (ANN이 찾은 상위 10개 ∩ 진짜 상위 10개) / 10

recall@10 = 0.95  →  진짜 상위 10개 중 9.5개를 찾았다
```

**recall 100%를 요구하면 완전 탐색과 같아진다.** 95%에서 99%로 올리는 비용이
80%에서 95%로 올리는 비용보다 훨씬 비싸다. **어디서 멈출지가 설계 결정이다.**

검색 결과가 추천이나 참고 문서라면 95%로 충분한 경우가 많다.
**중복 탐지나 법적 검토처럼 누락이 치명적이면 ANN이 적절하지 않을 수 있다.**

## 두 가지 대표 인덱스 — HNSW와 IVF

수많은 변형이 있지만 아이디어는 크게 둘이다.

### HNSW — 그래프를 따라 걸어간다

벡터들을 **가까운 것끼리 연결한 그래프**로 만들고, 계층을 쌓는다.

```text
상위 계층 (성긴 연결)   ●───────────●───────────●     멀리 점프
                         │           │
중간 계층                ●──●────●───●──●────●         좁혀 간다
                         │  │    │   │  │
하위 계층 (촘촘)         ●●●●●●●●●●●●●●●●●●●●●         정밀 탐색
```

지도에서 고속도로로 대략 이동한 뒤 국도로 좁혀 들어가는 것과 같다.
**속도와 recall이 모두 좋아서 기본 선택지로 많이 쓰인다.**

| 파라미터 | 의미 | 올리면 |
| --- | --- | --- |
| `M` | 노드당 연결 수 | recall ↑ · 메모리 ↑ |
| `ef_construction` | 색인할 때 탐색 폭 | 품질 ↑ · 색인 시간 ↑ |
| `ef_search` | 검색할 때 탐색 폭 | recall ↑ · **질의 지연 ↑** |

**`ef_search`는 질의 시점에 바꿀 수 있다.** 재색인 없이 "이번엔 정확하게"를 선택할 수 있는 손잡이다.

**대가는 메모리다.** 그래프 연결을 전부 들고 있어야 해서 원본 벡터보다 더 먹을 수 있다.

### IVF — 먼저 구역을 나눈다

벡터들을 미리 군집으로 나눠 두고, **질의와 가까운 군집 몇 개만** 뒤진다.

```text
전체를 nlist개 군집으로 분할
    ┌───┬───┬───┐
    │ A │ B │ C │     질의가 B 근처면
    ├───┼───┼───┤     B와 이웃 군집만 탐색 (nprobe개)
    │ D │ E │ F │     나머지는 아예 안 본다
    └───┴───┴───┘
```

| 파라미터 | 의미 |
| --- | --- |
| `nlist` | 군집 개수 |
| `nprobe` | 탐색할 군집 수 — **올리면 recall ↑, 속도 ↓** |

**메모리를 적게 쓰고 색인이 빠르다.** 대신 군집 경계에 걸친 벡터를 놓칠 수 있다.
데이터 분포가 바뀌면 군집이 낡아 재학습이 필요하다.

### 고를 때의 기준

```text
메모리에 여유가 있고 recall이 중요하다      →  HNSW
데이터가 아주 크고 메모리가 빠듯하다        →  IVF (+ 양자화)
데이터가 수만 건 수준이다                   →  ★ 그냥 완전 탐색
```

마지막 줄이 중요하다. **수만 건 규모에서는 ANN 인덱스가 필요 없다.**
완전 탐색이 충분히 빠르고, recall은 100%이며, 파라미터 튜닝도 필요 없다.
**인덱스를 안 쓰는 것이 정답인 구간이 실제로 존재한다.**

메모리가 부족하면 **양자화**(벡터를 압축해 저장)를 얹기도 한다.
저장 공간이 크게 줄지만 **정보를 버리는 것이라 정확도가 또 한 번 깎인다.**

## 벡터 DB가 관계형 DB와 다른 점

관계형 DB를 쓰던 감각이 어긋나는 지점들이다.

| | 관계형 DB | 벡터 DB |
| --- | --- | --- |
| 질의 | "같은 것을 찾아라" | **"가까운 것을 찾아라"** |
| 인덱스 | **정확**하다 (B-Tree) | **근사**다 (ANN) |
| 결과 | 조건을 만족하면 전부 | **항상 상위 k개** |
| 정답 | 하나로 정해진다 | **recall로 측정하는 확률적 품질** |
| 삭제 | 즉시 반영 | 그래프·군집 구조가 **점점 나빠진다** |
| 튜닝 대상 | 실행계획 | **recall vs 지연 vs 메모리** |

**"조건을 만족하는 행이 없으면 0건"이라는 감각이 없다.** 벡터 검색은 아무리 동떨어진 질의여도
**가장 가까운 k개를 돌려준다.** 관련 없는 결과도 "가장 덜 관련 없는 것"으로 올라온다.

그래서 **유사도 임계값으로 잘라내는 후처리**가 거의 항상 필요하다.
다만 그 임계값은 **모델마다 분포가 달라서** 직접 재서 정해야 한다.

## 필터링 — 실무에서 가장 자주 막히는 곳

"2026년 이후 문서 중에서 유사한 것"처럼 **조건과 벡터 검색을 함께** 쓰려는 순간 문제가 생긴다.

```text
방법 ①  후필터 (post-filter)
        벡터로 상위 100개 → 조건으로 거른다
        → 조건에 맞는 게 3개뿐일 수 있다  ★ 결과가 부족해진다

방법 ②  선필터 (pre-filter)
        조건으로 먼저 거른 뒤 그 안에서 벡터 검색
        → 후보가 좁아지면 ANN 인덱스를 제대로 못 쓴다  ★ 느려진다
```

**둘 다 완전한 답이 아니다.** 조건이 널널하면 후필터가, 아주 좁으면 선필터(사실상 완전 탐색)가 낫다.
제품마다 이 문제를 다루는 방식이 다르고, **벡터 DB를 고를 때 실제로 갈리는 지점**이기도 하다.

관계형 DB에서 `WHERE`를 자유롭게 조합하던 감각으로 접근하면 여기서 막힌다.

## 자주 하는 오해

### "벡터 검색이 키워드 검색을 대체한다"

아니다. **고유명사·제품 코드·숫자·오탈자**에는 키워드 검색이 더 강하다.
`ORD-2026-8841`을 찾을 때 의미적 유사도는 도움이 되지 않는다.

실무에서는 **하이브리드 검색**(키워드 + 벡터 점수 결합)이 단독보다 나은 경우가 많다.

### "코사인 유사도 0.8이면 비슷한 것이다"

**모델마다 점수 분포가 다르다.** 어떤 모델은 무관한 문장끼리도 0.7이 나오고,
어떤 모델은 거의 같은 문장이 0.85에 그친다.

**절대값에 기준을 걸지 말고, 자기 데이터로 분포를 재서 임계값을 정한다.**

### "벡터 DB를 쓰면 정확한 검색이 된다"

ANN은 **근사**다. 설정에 따라 진짜 가장 가까운 문서를 놓칠 수 있다.
정확도가 필수라면 완전 탐색을 쓰거나 recall을 측정해 관리해야 한다.

### "차원이 높을수록 좋다"

저장 공간과 계산량이 **선형으로** 늘고, 고차원일수록 거리들이 서로 비슷해지는 문제도 있다.
많은 모델이 **차원을 줄여 쓸 수 있는 옵션**을 제공하는 것은 이 때문이다.

### "임베딩은 한 번 만들면 끝이다"

모델 교체 = **전면 재색인**이다. 그리고 원본 문서가 바뀌면 그 벡터도 다시 만들어야 한다.
**임베딩 생성 비용과 재색인 절차를 처음부터 운영 계획에 넣어야 한다.**

## 정리

- 벡터 검색은 글자가 아니라 **의미의 거리**로 찾는다. 키워드 검색이 못 하던 것을 한다.
- 임베딩은 **같은 모델끼리만** 비교 가능하고, 모델을 바꾸면 **전면 재색인**이다.
- 정규화된 벡터에서는 코사인·내적·L2가 **같은 순위**를 준다. 모델 권장 척도를 따르면 된다.
- 완전 탐색은 `O(N × D)`라 N이 크면 버티지 못한다. B-Tree는 고차원에 쓸 수 없다.
- 그래서 **정확도를 팔아 속도를 산다.** 이것이 ANN이고, 품질은 **recall**로 잰다.
- **HNSW**는 빠르고 정확하지만 메모리를 먹고, **IVF**는 가볍지만 경계를 놓친다.
- **수만 건 규모면 인덱스 없이 완전 탐색이 정답**일 수 있다.
- 벡터 DB에는 "결과 0건"이 없다. **임계값 후처리가 필요하다.**
- **조건 필터와 벡터 검색의 결합**이 가장 자주 막히는 지점이다.

## 학습 체크리스트

- [ ] 키워드 검색이 못 하고 벡터 검색이 하는 일을 예로 설명할 수 있다
- [ ] 임베딩 모델을 바꾸면 왜 전면 재색인이 필요한지 말할 수 있다
- [ ] 정규화된 벡터에서 세 척도의 순위가 같아지는 이유를 안다
- [ ] B-Tree를 벡터 검색에 쓸 수 없는 이유를 설명할 수 있다
- [ ] recall이 무엇이고 왜 100%를 목표로 하지 않는지 말할 수 있다
- [ ] HNSW와 IVF의 트레이드오프를 메모리·속도·recall로 비교할 수 있다
- [ ] 후필터와 선필터가 각각 어디서 깨지는지 설명할 수 있다
