# 넷퍼널(NetFUNNEL)은 아키텍처의 어디에 놓이는가

## 학습 목적

티켓팅, 수강신청, 한정판 판매처럼 **특정 시각에 트래픽이 수직으로 솟는** 서비스를 설계할 때
"서버를 늘리면 되지 않나"라는 답이 왜 통하지 않는지, 그리고 그 자리에 왜 가상 대기실이 들어가는지를 정리한다.

이 글이 답하는 질문은 세 가지다.

- 오토스케일링이 있는데도 대기열이 필요한 이유는 무엇인가
- 넷퍼널은 아키텍처의 어느 계층에 붙고, 계층마다 무엇을 포기하는가
- 진입 허용 수는 어떤 근거로 정하고, 잘못 정하면 무슨 일이 생기는가

제품의 내부 알고리즘이 아니라 **아키텍처 설계자 입장에서의 배치와 트레이드오프**를 다룬다.

## 스케일아웃이 못 푸는 문제

동시접속 100만을 처리한다고 할 때, 흔히 웹 서버 대수를 먼저 떠올린다.
하지만 티켓팅에서 실제로 터지는 지점은 웹 서버가 아니다.

```text
사용자 100만
   │
   ▼
[CDN]            정적 자원 — 얼마든지 스케일아웃 가능
   │
   ▼
[웹/WAS]         무상태 — 인스턴스 늘리면 됨
   │
   ▼
[DB / 재고 / PG] ★ 여기가 병목. 늘릴 수 없다
```

- **재고와 좌석**은 정의상 직렬화되어야 한다. "A11석"은 한 명만 가질 수 있고, 이 판정은 결국 한 곳에서 순서를 정해야 한다.
- **결제 PG**는 우리가 스케일아웃할 수 있는 대상이 아니다. 계약된 TPS가 상한이다.
- **RDB의 쓰기**는 읽기 복제본을 아무리 늘려도 프라이머리 한 대로 모인다.

즉 시스템 전체 처리율은 **가장 느린 구간의 처리율**로 고정된다.
앞단만 늘리면 병목 앞에 요청이 쌓일 뿐이고, 쌓인 요청은 커넥션 풀 고갈 → 타임아웃 → 재시도 →
부하 증폭이라는 익숙한 순서로 서비스를 무너뜨린다.

### 큐잉 이론으로 보면 더 분명하다

도착률을 λ, 처리율을 μ라고 할 때 λ > μ 이면 대기 행렬은 시간에 비례해 무한히 늘어나고
응답 시간은 발산한다. 여기서 선택지는 두 개뿐이다.

| 선택 | 방법 | 한계 |
| --- | --- | --- |
| μ를 키운다 | 스케일아웃, 캐시, 쿼리 튜닝 | 재고·PG·프라이머리 DB에는 상한이 있다 |
| λ를 줄인다 | **대기열, 레이트 리밋, 큐잉** | 사용자를 기다리게 만든다 |

μ를 더 못 키우는 순간부터는 λ를 제어하는 것 외에 방법이 없다.
**가상 대기실은 λ를 시스템이 감당 가능한 상수로 고정하는 장치다.**

## 대기열이 실제로 바꾸는 것

대기열을 넣는다고 처리량이 늘지는 않는다. 바뀌는 것은 **실패의 모양**이다.

```text
대기열 없음                     대기열 있음
─────────────                   ─────────────
전원 진입 시도                   N명만 진입
   ↓                               ↓
전원 느려짐                      진입한 N명은 정상 속도
   ↓                               ↓
전원 타임아웃                    나머지는 "3분 후 입장" 안내
   ↓
아무도 성공 못 함                N명은 확실히 성공
```

왼쪽은 100만 명이 모두 실패한다. 오른쪽은 순서대로 전원이 성공한다.
총 처리 시간은 오히려 오른쪽이 짧다. 재시도 폭풍이 없기 때문이다.

이것이 대기열의 본질이다. **처리량을 늘리는 기술이 아니라, 초과분을 유실 대신 지연으로 바꾸는 기술이다.**

## 넷퍼널의 구성

넷퍼널은 에스티씨랩(STCLab)이 만든 가상 대기실 솔루션이다.
공식 문서 기준 구성은 세 덩어리다.

| 구성 요소 | 위치 | 역할 |
| --- | --- | --- |
| 경량 에이전트 | 고객사 서비스 환경 | 요청을 가로채 진입 여부를 판정 |
| 넷퍼널 서버 | 넷퍼널 측 | 트래픽 상황과 임계값을 보고 진입 가능 여부 결정 |
| 콘솔 | 넷퍼널 측 | 트리거 규칙 설정, 실시간 모니터링 |

동작 흐름은 다음과 같다.

```text
① 사용자가 페이지 접속
② 에이전트 로드 및 초기화
③ 에이전트가 제어 조건(트리거 규칙) 확인
④ 넷퍼널 서버와 통신 — TTL 기반으로 상태 갱신
       ├─ 임계값 초과 ─▶ 가상 대기실로 이동, 순번 부여
       └─ 여유 있음   ─▶ 즉시 서비스 진입
⑤ 대기 중인 사용자는 순번에 따라 자동 리다이렉트
```

핵심은 ④다. **판정은 에이전트가 매번 원격 호출로 묻는 것이 아니라, TTL 기반으로 갱신된 상태를 보고 로컬에서 내린다.**
매 요청마다 중앙에 물으면 그 중앙이 새 병목이 되기 때문이다. 대신 그 대가로 진입 수는 근사치가 된다.

## 어느 계층에 붙일 것인가

넷퍼널이 흥미로운 것은 **붙일 수 있는 지점이 세 곳**이고, 각각 방어 범위가 다르다는 점이다.
개발자 가이드는 클라이언트 / 서버 / 엣지로 나뉜다.

```text
사용자
  │
  ├─[엣지]      Akamai · CloudFront · Cloudflare · Fastly
  │                 요청이 오리진에 닿기 전에 차단
  ▼
[클라이언트]   Web · Android · iOS · React-Native · Flutter
  │                 화면 진입 시점에 대기실 표시
  ▼
[서버]         Java · Node.js
                    Filter / Interceptor 에서 최종 검증
```

### 세 방식의 트레이드오프

| 방식 | 오리진 부하 | 우회 가능성 | 적용 비용 |
| --- | --- | --- | --- |
| 엣지 | **가장 낮음** — 오리진에 안 옴 | 낮음 | 엣지 함수 배포 필요 |
| 클라이언트 | 정적 자원 요청은 발생 | **높음** — API 직접 호출로 뚫림 | 태그 한 줄 |
| 서버 | 요청은 도달함 | 낮음 | 코드 수정 필요 |

**클라이언트 태그만 붙이는 것은 위험하다.** 대기실은 브라우저에서 그려지는 화면일 뿐이고,
개발자 도구로 API 엔드포인트를 확인해 직접 호출하면 대기열을 지나치게 된다.
매크로가 도는 티켓팅에서는 이 우회가 곧바로 문제가 된다.

실무에서는 **엣지 또는 서버에서 최종 판정하고, 클라이언트는 사용자 경험(순번 표시)을 담당**하는 이중 구성이 안전하다.

### 웹 클라이언트 적용

스크립트는 `<head>` 상위에 넣는다. 서비스 로직보다 먼저 초기화되어야 하기 때문이다.

```html
<script
  src="{{AGENT_URL}}"
  data-nf-client-id="{{CLIENT_ID}}"
></script>
```

코드로 제어할 때는 진입(`nfStart`)과 통과(`nfStop`)를 짝으로 호출한다.

```javascript
// 진입 요청 — 허용될 때까지 대기실이 뜬다
nfStart({
  projectKey: "{{PROJECT_KEY}}",
  segmentKey: "{{SEGMENT_KEY}}"
}, function (response) {
  nfCallback(response);
});

// 작업이 끝나 슬롯을 반납
nfStop({
  projectKey: "{{PROJECT_KEY}}",
  segmentKey: "{{SEGMENT_KEY}}"
});
```

`nfStop`을 빠뜨리면 슬롯이 반납되지 않아 뒤에 있는 대기자가 들어오지 못한다.
try/finally에 해당하는 위치에 넣어야 한다.

### 서버(Java) 적용

Java 에이전트는 Spring의 **Interceptor** 또는 서블릿 **Filter**에 붙인다.

```java
// Interceptor 방식
public boolean preHandle(HttpServletRequest request,
                         HttpServletResponse response,
                         Object handler) {
    NetFunnelInitialize config = NetFunnelInitialize.Companion.builder()
        .clientId("{{CLIENT_ID}}")
        .secretKey("{{SECRET_KEY}}")
        .build();
    Netfunnel netfunnel = new Netfunnel(config,
        new NetFunnelServletService(request, response), null, null);
    return netfunnel.run();   // false면 대기실로 보내고 컨트롤러 실행 안 함
}
```

```java
// Filter 방식
public void doFilter(ServletRequest servletRequest,
                     ServletResponse servletResponse,
                     FilterChain chain) {
    Netfunnel netfunnel = new Netfunnel(config,
        new NetFunnelServletService(request, response), null, null);
    if (!netfunnel.run()) return;      // 대기 대상이면 여기서 끊는다
    chain.doFilter(servletRequest, servletResponse);
}
```

두 방식 중 **Filter를 권한다.** Interceptor는 컨트롤러 매핑을 거친 뒤 동작하므로 경로 패턴이
컨트롤러 매핑과 어긋날 수 있고, Spring 공식 문서도 같은 이유로 인터셉터를 보안 계층으로 쓰지 말라고 권고한다.
대기열 우회는 보안 문제와 성격이 같다.
Filter와 Interceptor의 위치 차이는 [Django 개발자를 위한 Spring 지도](../backend/2026-08-24-django-to-spring-map.md)에 정리해 두었다.

판정 결과는 **쿠키**로 유지된다. 그래서 `cookieDomain` 설정이 중요하다.
`www`와 `order` 같은 서브도메인을 오가는 서비스라면 상위 도메인으로 맞춰야 대기열을 다시 타지 않는다.

### 엣지(CloudFront) 적용

CloudFront에서는 Lambda@Edge의 **뷰어 요청**과 **뷰어 응답** 두 이벤트에 붙는다.

- 뷰어 요청에서 트리거 규칙과 대조해 제어 대상이면 대기실 페이지로 리다이렉트한다.
- 대기실 도메인은 `agent-lib.stclab.com`이다. 즉 **대기 중 트래픽은 우리 오리진에 오지 않는다.**
- User-Agent에 굿봇 키워드가 있으면 제어 대상에서 제외한다. 검색 엔진 크롤러가 대기실 페이지를 색인하는 사고를 막기 위해서다.
- Lambda 함수는 `us-east-1`에서 만들어야 한다. Lambda@Edge의 제약이다.

엣지 방식의 가장 큰 이점은 여기 있다. **대기실 자체의 트래픽조차 우리 인프라 비용이 아니다.**
자체 구현 대기열은 100만 명의 폴링을 우리가 받아야 한다.

## 세그먼트 설계

넷퍼널의 제어 단위는 **세그먼트**다. 프로젝트 아래에 세그먼트를 만들고, 세그먼트마다 트리거 규칙과 진입 허용 수를 건다.

### 기본 제어와 구간 제어

| | 기본 제어 | 구간 제어 |
| --- | --- | --- |
| API | `nfStart` / `nfStop` | `nfStartSection` / `nfStopSection` |
| 슬롯 점유 | 진입 시점만 | **시작~종료 전 구간** |
| 적합한 경우 | 단일 페이지 진입 | 좌석 선택→결제 같은 다단계 |

공식 문서 표현으로는 구간 제어는 "시작과 종료 사이의 모든 시간을 활동 구간으로 간주하여 다음 대기자를 진입시키지 않습니다".

티켓팅에서는 이 차이가 결정적이다. 기본 제어로 진입만 막으면
좌석 선택 중인 사용자와 새로 들어온 사용자가 겹쳐 결제 단계가 다시 터진다.
**결제 슬롯을 점유 단위로 잡아야** 병목 구간의 동시 사용자 수가 실제로 제한된다.

### 주요 설정 항목

| 항목 | 범위 | 의미 |
| --- | --- | --- |
| 진입 허용 수 | 고정형 / 변동형 | 0으로 두면 전원 대기실로 보낸다(오픈 전 사전 대기) |
| 진입 제어 모델 | 변동 진입형 / 고정 진입형 | 실시간 최적화냐, 정확한 순번 안내냐 |
| 재요청 주기 | 1~60초 | 클라이언트가 진입 가능 여부를 확인하는 빈도 |
| 타임아웃 | 6~60초 | 쓰이지 않은 슬롯을 자동 회수 |
| 대기 순번 유지 | 1초~2시간 | 연결이 끊겨도 순번 복원 |
| 진입 패스 | 1분~24시간 | 한 번 통과하면 재대기 없이 재진입 |

세그먼트 키는 **생성 후 변경할 수 없다.** 코드에 하드코딩하기 전에 명명 규칙을 정해 두는 편이 낫다.

**재요청 주기**는 대기실 품질과 비용을 동시에 결정한다.
1초로 두면 순번이 촘촘히 갱신되지만 대기자 100만 명이 초당 100만 요청을 만든다.
넷퍼널 인프라가 받아 주더라도, 사용자 단말의 배터리와 네트워크는 우리 몫이 아니라고 말하기 어렵다.

## 진입 허용 수는 어떻게 정하는가

이 값이 아키텍처 설계의 핵심 숫자다. **추측으로 정하면 대기열을 넣은 의미가 없다.**

1. **부하 테스트로 μ를 측정한다.** 병목 구간(결제, 재고 차감)이 응답 시간을 유지하며 감당하는 TPS를 찾는다.
2. **안전 계수를 곱한다.** 측정값의 70~80% 정도로 잡는다. 측정 환경과 실제는 늘 다르다.
3. **점유 시간을 반영한다.** 리틀의 법칙 `동시 사용자 = 처리율 × 체류 시간`을 뒤집어 쓴다.
   결제까지 평균 3분이 걸리고 결제 병목이 초당 10건이면, 구간 제어의 동시 허용 수는 대략 `10 × 180 = 1,800`이 된다.
4. **오픈 후 조정한다.** 콘솔에서 실시간으로 바꿀 수 있는 값이다. 첫 오픈에 정답을 맞출 수는 없다.

낮게 잡으면 대기 시간이 길어지고, 높게 잡으면 대기열을 통과한 사용자가 실패한다.
**후자가 훨씬 나쁘다.** 30분 기다려 들어갔는데 오류를 만나는 경험은 대기열이 없는 것보다 나쁘다.
그래서 초기값은 보수적으로 잡는 편이 맞다.

## 대기 순번은 정확한가

넷퍼널은 두 가지 모델을 제공하고, 정확도는 여기서 갈린다.

- **변동 진입형**: 실시간 상황을 반영해 진입을 처리한다. 처리량은 최적이지만 예상 시간이 흔들린다.
- **고정 진입형**: 일정한 주기로 진입시키고, 그 주기를 근거로 대기 정보를 전달한다. 안내가 정확한 대신 여유 자원을 놀릴 수 있다.

다만 고정 진입형이어도 예상 시간은 확정이 아니다. 제공사 설명은 이렇게 말한다.

> "처리 시간이 짧고, 허수 이용자의 비율이 크다면 실제 대기 시간이 빠르게 줄어들 수 있습니다.
> 반대로 이용 시간이 길어지고 허수 이용자가 많다면 처음 안내된 대기 시간보다 오래 대기하는 경우도 발생할 수 있습니다."

여기서 **허수 이용자**란 대기 순번을 받아 놓고 실제로는 들어오지 않는 사람이다.
이들이 많으면 줄이 예상보다 빨리 줄고, 반대로 한 사람당 체류가 길어지면 느려진다.
**"예상 시간"은 UX 장치지 SLA가 아니다.** 이 점을 CS 응대 기준에도 반영해 둬야 한다.

## 운영에서 밟는 지뢰

- **대기실이 새로운 SPOF가 된다.** 넷퍼널 서버에 장애가 나면 어떻게 할지 정해야 한다. 에이전트가 판정을 못 할 때 통과시킬 것인가(fail-open) 막을 것인가(fail-closed). 티켓팅이면 fail-closed, 일반 커머스면 fail-open이 보통 맞다.
- **API 직접 호출 우회.** 앞서 말한 대로 클라이언트 전용 적용은 뚫린다. 모바일 앱은 SDK가 있어도 중간자 프록시로 우회 가능하니 서버 검증이 최종 방어선이다.
- **새로고침과 중복 탭.** 사용자는 안 열리면 F5를 누른다. 순번 유지 설정과 쿠키가 제대로 걸려 있지 않으면 누를 때마다 뒤로 밀리고, 그러면 사용자는 더 누른다.
- **대기실 페이지 자체의 무게.** 대기실은 100만 명이 보는 페이지다. 이미지와 스크립트를 최소화해야 한다.
- **오픈 전 사전 대기.** 오픈 1분 전부터 사람이 몰린다. 진입 허용 수를 0으로 두고 사전 대기실을 여는 구성이 필요하다. 넷퍼널은 사전 / 기본 / 사후 대기실과 차단실을 구분해 제공한다.
- **모니터링 이중화.** 넷퍼널 콘솔의 지표와 우리 APM 지표를 같이 봐야 한다. "대기열은 초당 10명을 넣고 있는데 우리 서버는 초당 3건밖에 못 하고 있다"를 실시간으로 알아채야 한다. 모니터링 도구 선택은 [모니터링 스택 비교](../../devops/2026-08-06-monitoring-stack-comparison.md)를 참고한다.

## 대기열 앞뒤로 무엇이 더 필요한가

가상 대기실은 만능이 아니다. 인접한 방어 수단과 역할이 다르다.

| 계층 | 도구 | 막는 것 |
| --- | --- | --- |
| 유입 제어 | 가상 대기실(넷퍼널) | 정상 사용자의 동시 유입량 |
| 요청 제어 | Rate Limit | 한 사용자의 과도한 요청 빈도 |
| 자원 경합 | 원자적 연산 / 락 | 재고 초과 판매 |
| 악성 트래픽 | WAF, 봇 차단 | 매크로, 크롤러 |

대기열을 통과한 뒤에도 **재고가 음수가 되는 문제는 그대로 남는다.**
동시 진입자가 1,800명이면 그 1,800명 사이의 경합은 여전히 원자적으로 처리해야 한다.
이 부분은 [Redis Lua 스크립트로 동시성 문제 풀기](../backend/2026-08-23-redis-lua-atomic-patterns.md)에 정리했다.

직접 구현할지 솔루션을 살지는 결국 **대기실 트래픽을 누가 받느냐**의 문제다.
Redis 기반으로 직접 만들면 100만 명의 폴링을 우리 인프라가 받아야 하고,
그 폴링 서버를 지키기 위해 또 다른 대기열이 필요해지는 순환에 빠지기 쉽다.
상용 솔루션의 값은 기능이 아니라 **그 트래픽을 대신 받아 주는 것**에 붙는다.

## 자주 하는 오해

**"대기열을 넣으면 더 많이 처리할 수 있다"**
아니다. 처리량은 그대로다. 초과분을 유실이 아니라 지연으로 바꿀 뿐이다.
처리량을 늘리려면 병목 자체를 손봐야 한다.

**"오토스케일링이 있으면 필요 없다"**
오토스케일링은 반응에 수십 초에서 수 분이 걸리고, 무상태 계층만 늘릴 수 있다.
티켓팅의 피크는 몇 초 만에 온다. 그리고 재고와 PG는 스케일아웃 대상이 아니다.

**"클라이언트에 태그만 붙이면 된다"**
대기실은 화면일 뿐이다. API를 직접 호출하면 지나칠 수 있다.
매크로가 도는 환경이라면 엣지나 서버에서 최종 판정해야 한다.

**"예상 대기 시간은 정확하다"**
허수 이용자 비율과 실제 체류 시간에 따라 흔들린다. 확정 값이 아니다.

**"넷퍼널을 넣으면 동시성 문제가 해결된다"**
유입량만 줄어든다. 통과한 사용자들 사이의 재고 경합은 그대로 남는다.

## 정리

- 대규모 동시접속의 병목은 웹 서버가 아니라 **스케일아웃할 수 없는 자원**(재고, PG, 프라이머리 DB)이다.
- μ를 더 못 키우면 λ를 제어해야 한다. 가상 대기실은 λ를 상수로 고정하는 장치다.
- 넷퍼널은 **경량 에이전트 + 넷퍼널 서버 + 콘솔** 구성이고, 에이전트는 TTL 기반 상태로 로컬 판정한다.
- 적용 지점은 **엣지 / 클라이언트 / 서버** 세 곳. 클라이언트 단독은 API 직접 호출로 우회된다.
- 다단계 흐름은 **구간 제어**로 잡아야 병목 구간의 동시 사용자 수가 실제로 제한된다.
- 진입 허용 수는 **부하 테스트로 측정한 병목 TPS × 안전 계수**로 정한다. 높게 잡는 실패가 낮게 잡는 실패보다 나쁘다.
- 대기실은 새로운 SPOF다. fail-open / fail-closed를 서비스 성격에 맞게 미리 정한다.

## 학습 체크리스트

- [ ] 오토스케일링이 있는데도 대기열이 필요한 이유를 병목 자원 관점에서 설명할 수 있는가
- [ ] 대기열이 처리량을 늘리지 않는다는 것을 λ와 μ로 설명할 수 있는가
- [ ] 엣지 / 클라이언트 / 서버 적용의 우회 가능성 차이를 설명할 수 있는가
- [ ] 기본 제어와 구간 제어를 언제 나눠 쓰는지 티켓팅 예로 설명할 수 있는가
- [ ] 진입 허용 수를 리틀의 법칙으로 추정할 수 있는가
- [ ] 예상 대기 시간이 흔들리는 조건(허수 이용자, 체류 시간)을 설명할 수 있는가
- [ ] 대기열 통과 후에도 남는 동시성 문제가 무엇인지 말할 수 있는가
