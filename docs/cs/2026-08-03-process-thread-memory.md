## 학습 목적

"프로세스는 자원의 단위이고 스레드는 실행의 단위" 같은 문장은 외우기는 쉽지만, 실제로 워커 수를 정하거나 메모리 사용량을 계산할 때는 도움이 되지 않는다. 왜 스레드 전환이 더 싼지, 왜 프로세스를 늘리면 메모리가 그만큼 늘지 않는지 설명하려면 메모리가 실제로 어떻게 배치되고 공유되는지 알아야 한다.

이 글에서는 프로세스와 스레드의 차이를 **메모리 구조를 중심으로** 정리하고, 이어서 컨텍스트 스위칭 비용, 통신 방식, 장애 격리, 런타임별 구현 차이처럼 함께 알아두면 좋은 내용을 다룬다.

## 두 개념의 정의

| 구분 | 정의 | 운영체제가 관리하는 것 |
| --- | --- | --- |
| 프로세스 | 실행 중인 프로그램의 인스턴스 | 독립된 가상 주소 공간, 파일 디스크립터 테이블, 권한, 자원 한도 |
| 스레드 | 프로세스 안에서 실행 흐름을 담당하는 단위 | 스택, 레지스터 상태, 스케줄링 정보 |

프로그램은 디스크에 있는 실행 파일이고, 프로세스는 그 프로그램이 메모리에 올라가 실행되는 상태다. 하나의 프로세스는 최소 하나의 스레드(메인 스레드)를 가지며, 스레드를 추가로 만들면 같은 주소 공간을 공유하는 실행 흐름이 늘어난다.

스케줄링 관점에서 보면 CPU에 올라가는 것은 프로세스가 아니라 **스레드**다. 리눅스 커널은 실제로 프로세스와 스레드를 모두 `task_struct`라는 같은 구조체로 관리하고, 주소 공간을 공유하는지 여부로 둘을 구분한다.

## 프로세스의 메모리 배치

프로세스가 사용하는 가상 주소 공간은 목적에 따라 영역이 나뉜다.

```text
높은 주소
┌─────────────────────────────┐
│ Stack                       │  지역 변수, 함수 인자, 복귀 주소
│   │ (아래로 성장)            │
│   ▼                         │
├─────────────────────────────┤
│ (빈 공간)                    │
├─────────────────────────────┤
│   ▲                         │
│   │ (위로 성장)              │
│ Heap                        │  malloc, new로 할당한 동적 메모리
├─────────────────────────────┤
│ Memory-mapped region        │  공유 라이브러리, mmap 파일
├─────────────────────────────┤
│ BSS                         │  초기값 없는 전역·정적 변수 (0으로 초기화)
├─────────────────────────────┤
│ Data                        │  초기값 있는 전역·정적 변수
├─────────────────────────────┤
│ Text (Code)                 │  실행할 기계어 (읽기 전용)
└─────────────────────────────┘
낮은 주소
```

각 영역의 성격은 다음과 같다.

| 영역 | 저장 내용 | 수명 | 특징 |
| --- | --- | --- | --- |
| Text | 컴파일된 기계어 | 프로세스 종료까지 | 읽기 전용이라 같은 실행 파일을 쓰는 프로세스끼리 물리 메모리를 공유할 수 있다 |
| Data | 초기값이 있는 전역·정적 변수 | 프로세스 종료까지 | 실행 파일에 초기값이 기록되어 있다 |
| BSS | 초기값이 없는 전역·정적 변수 | 프로세스 종료까지 | 실행 파일에는 크기만 기록되고 실행 시 0으로 채워진다 |
| Heap | 동적 할당 메모리 | 해제할 때까지 | 크기가 실행 중에 변하며 단편화가 생길 수 있다 |
| Stack | 지역 변수, 함수 호출 프레임 | 함수 반환까지 | 할당·해제가 빠르고 크기 한도가 정해져 있다 |

## 스레드가 공유하는 것과 갖는 것

핵심은 여기다. 스레드를 추가해도 **주소 공간은 하나**이고, 스택만 스레드마다 따로 생긴다.

```text
프로세스 (하나의 가상 주소 공간)
┌───────────────────────────────────────────────────┐
│  Text  │  Data  │  BSS  │  Heap  │  mmap 영역      │  ← 모든 스레드가 공유
├───────────────────────────────────────────────────┤
│ ┌──────────┐  ┌──────────┐  ┌──────────┐          │
│ │ Thread 1 │  │ Thread 2 │  │ Thread 3 │          │
│ │  Stack   │  │  Stack   │  │  Stack   │          │  ← 스레드마다 별도
│ │  레지스터 │  │  레지스터 │  │  레지스터 │          │
│ │  TLS     │  │  TLS     │  │  TLS     │          │
│ └──────────┘  └──────────┘  └──────────┘          │
└───────────────────────────────────────────────────┘
```

| 항목 | 스레드 간 공유 | 설명 |
| --- | --- | --- |
| Text (코드) | 공유 | 같은 함수를 여러 스레드가 실행한다 |
| Data / BSS (전역 변수) | 공유 | 전역 상태를 동시에 건드리면 경쟁 상태가 생긴다 |
| Heap | 공유 | 한 스레드가 할당한 객체를 다른 스레드가 그대로 참조할 수 있다 |
| 파일 디스크립터 | 공유 | 한 스레드가 연 소켓·파일을 다른 스레드가 읽고 쓸 수 있다 |
| 시그널 핸들러, 작업 디렉터리, PID | 공유 | 프로세스 단위 속성이다 |
| **Stack** | **독립** | 지역 변수는 스레드마다 분리된다 |
| **레지스터 (PC, SP 등)** | **독립** | 각자 어느 코드를 실행 중인지 다르다 |
| **TLS (Thread Local Storage)** | **독립** | 전역처럼 쓰지만 스레드마다 값이 다른 저장소다 |
| **시그널 마스크, errno, 스레드 ID** | **독립** | 스레드별로 관리된다 |

프로세스 간에는 이 표의 거의 전부가 독립이다. 다른 프로세스의 힙에 있는 객체를 포인터로 접근할 수 없고, 그러려면 명시적으로 공유 메모리를 설정해야 한다.

### 지역 변수는 안전하고 전역 변수는 위험한 이유

이 구조가 바로 "지역 변수는 스레드 안전하지만 전역 변수는 아니다"라는 말의 근거다.

```python
counter = 0  # Data/BSS 영역 -> 모든 스레드가 같은 메모리를 본다


def worker():
    local_sum = 0     # Stack 영역 -> 스레드마다 별도 메모리
    for _ in range(100_000):
        local_sum += 1
        counter += 1  # 여러 스레드가 같은 주소를 동시에 갱신 -> 경쟁 상태
```

`local_sum`은 스레드마다 다른 스택에 있으므로 서로 간섭하지 않는다. 반면 `counter`는 하나의 주소를 여러 스레드가 함께 갱신하므로 값이 유실될 수 있다.

### TLS: 전역처럼 쓰되 스레드마다 분리하기

요청 ID, 로그인 사용자, DB 커넥션처럼 "함수 인자로 넘기기는 번거롭지만 스레드마다 달라야 하는 값"은 TLS에 둔다.

```python
import threading

local_data = threading.local()


def handle_request(request_id: str) -> None:
    local_data.request_id = request_id  # 이 스레드에서만 보이는 값
    process()


def process() -> None:
    print(local_data.request_id)  # 인자로 넘기지 않아도 접근 가능
```

Java의 `ThreadLocal`, Go의 `context.Context`(명시적 전달 방식)가 같은 문제를 다룬다. 다만 스레드 풀에서는 스레드가 재사용되므로 **작업이 끝날 때 값을 정리하지 않으면 다음 요청에 이전 값이 남는다.** 실무에서 자주 나오는 버그다.

### 스택 크기가 스레드 수를 제한한다

스레드마다 스택을 따로 잡으므로, 스레드 수는 메모리와 직결된다. 리눅스 glibc의 기본 스레드 스택 크기는 보통 8MB다.

```bash
ulimit -s          # 스택 크기 확인 (KB 단위, 흔히 8192)
```

스레드 1,000개면 산술적으로 8GB지만 실제로 그만큼 쓰지는 않는다. **가상 메모리로 예약만 하고 실제로 건드린 페이지만 물리 메모리에 할당**되기 때문이다. 그래도 가상 주소 공간과 커널 자료구조는 소비되므로, 스레드를 수만 개 만드는 설계는 이 지점에서 한계에 부딪힌다.

Go의 고루틴이 수십만 개까지 가능한 이유가 여기 있다. 고루틴은 OS 스레드가 아니라 런타임이 관리하는 실행 단위이고, 초기 스택이 약 2KB로 작게 시작해 필요할 때 커진다.

## 가상 메모리 관점에서 본 진짜 차이

지금까지의 차이는 결국 **페이지 테이블을 공유하는가**로 요약된다.

프로세스가 사용하는 주소는 물리 주소가 아니라 가상 주소다. CPU의 MMU가 페이지 테이블을 참조해 가상 주소를 물리 주소로 변환한다.

```text
프로세스 A                        프로세스 B
가상 주소 0x400000               가상 주소 0x400000
      │                                │
      ▼ 페이지 테이블 A                  ▼ 페이지 테이블 B
물리 주소 0x1A2B000              물리 주소 0x7F3C000
      (서로 다른 물리 메모리 -> 완전히 격리)

같은 프로세스의 스레드 1, 2
가상 주소 0x400000  ──┐
                     ├─▶ 같은 페이지 테이블 ─▶ 같은 물리 주소
가상 주소 0x400000  ──┘
```

- **프로세스마다 페이지 테이블이 따로 있다.** 그래서 같은 가상 주소가 서로 다른 물리 메모리를 가리키고, 남의 메모리를 읽을 수 없다.
- **같은 프로세스의 스레드는 페이지 테이블을 공유한다.** 그래서 포인터 하나를 그대로 주고받을 수 있다.

### Copy-on-Write: 프로세스 생성이 생각보다 싼 이유

`fork()`로 프로세스를 복제할 때 메모리 전체를 실제로 복사하지는 않는다. 부모와 자식이 같은 물리 페이지를 **읽기 전용으로 공유**하다가, 어느 쪽이든 쓰기를 시도하는 순간 그 페이지만 복사한다. 이것이 Copy-on-Write(CoW)다.

```text
fork() 직후          부모와 자식이 같은 물리 페이지를 공유 (읽기 전용)
자식이 페이지 X에 쓰기  →  페이지 X만 복사해서 자식 전용으로 교체
나머지 페이지          여전히 공유
```

실무에서 중요한 결과가 두 가지 있다.

1. **워커 프로세스 N개의 메모리가 단순히 N배가 아니다.** Gunicorn이나 uWSGI에서 `preload_app`을 켜면 앱을 먼저 로드한 뒤 fork하므로, 코드와 초기 데이터를 공유해 메모리를 절약할 수 있다.
2. **참조 카운팅 언어에서는 CoW 효과가 줄어든다.** Python은 객체를 읽기만 해도 참조 카운트가 바뀌어 해당 페이지에 쓰기가 발생하고, 결국 페이지가 복사된다. 그래서 기대만큼 메모리가 절약되지 않을 수 있다.

### 컨텍스트 스위칭 비용의 근거

CPU가 실행 대상을 바꿀 때 필요한 작업이 다르다.

| 전환 종류 | 저장·복원 대상 | 추가 비용 |
| --- | --- | --- |
| 같은 프로세스 내 스레드 전환 | 레지스터, 스택 포인터, 프로그램 카운터 | 없음 (페이지 테이블 그대로) |
| 다른 프로세스로 전환 | 위 항목 + 페이지 테이블 교체 | TLB 무효화, 캐시 지역성 손실 |

MMU는 주소 변환 결과를 TLB(Translation Lookaside Buffer)라는 캐시에 저장해 둔다. 프로세스가 바뀌면 이 캐시의 내용이 더 이상 유효하지 않으므로 비우거나 걸러내야 하고, 이후 한동안 주소 변환이 느려진다. CPU 캐시에 남아 있던 데이터도 쓸모없어진다.

**이 "이후에 느려지는 부분"이 전환 자체의 비용보다 큰 경우가 많다.** 최신 x86-64는 PCID, ARM은 ASID로 페이지 테이블마다 태그를 붙여 전체 무효화를 피하지만, 캐시 지역성이 깨지는 문제는 남는다.

절대 수치는 CPU, 커널 버전, 워크로드에 따라 크게 달라지므로 외우기보다 **순서를 기억하는 편이 유용하다.**

```text
함수 호출  <<  스레드 전환  <  프로세스 전환  <<  디스크 I/O
(나노초)      (마이크로초)                        (밀리초)
```

## 통신 방식의 차이

메모리를 공유하는지 여부는 통신 방식도 결정한다.

### 스레드 간 통신

같은 힙을 보므로 변수를 그대로 공유하면 된다. 대신 **동기화가 전부 개발자 책임**이다.

```python
import threading

shared = []
lock = threading.Lock()


def worker(value: int) -> None:
    with lock:          # 임계 구역 보호
        shared.append(value)
```

빠르지만, 경쟁 상태·데드락·가시성 문제를 직접 관리해야 한다.

### 프로세스 간 통신 (IPC)

주소 공간이 분리되어 있으므로 커널이 제공하는 수단을 거쳐야 한다.

| 방식 | 특징 | 사용 예 |
| --- | --- | --- |
| 파이프 / 이름 있는 파이프 | 단방향 바이트 스트림, 간단함 | 셸의 `\|`, 부모-자식 프로세스 |
| 메시지 큐 | 메시지 단위 송수신, 커널이 버퍼링 | 프로세스 간 작업 전달 |
| 공유 메모리 | 가장 빠름, 물리 페이지를 여러 프로세스에 매핑 | 대용량 데이터 공유 |
| 소켓 | 같은 장비와 네트워크 모두 지원 | 서버-클라이언트, 마이크로서비스 |
| 시그널 | 이벤트 알림만 가능, 데이터 전달 불가 | 종료 요청(`SIGTERM`) |
| 메모리 맵 파일 | 파일을 주소 공간에 매핑해 공유 | 대용량 파일 처리 |

공유 메모리는 커널을 거치는 복사 과정이 없어 가장 빠르지만, 결국 **스레드와 같은 동기화 문제**를 그대로 떠안게 된다. 그 외 방식은 데이터를 직렬화해 복사하므로 안전한 대신 비용이 든다.

Python `multiprocessing`으로 프로세스 풀을 쓸 때 큰 DataFrame을 인자로 넘기면 느려지는 이유가 이것이다. 계산 시간보다 직렬화·전송 비용이 커질 수 있다.

## 장애 격리

메모리 격리는 안정성 차이로 직결된다.

- **스레드**: 하나가 세그먼테이션 폴트를 내면 프로세스 전체가 죽는다. 다른 스레드가 정상이어도 함께 종료된다. 메모리를 공유하므로 한 스레드의 메모리 손상이 다른 스레드에 번질 수도 있다.
- **프로세스**: 하나가 죽어도 나머지는 영향을 받지 않는다. 부모가 이를 감지해 새 워커를 띄우면 서비스가 유지된다.

크롬이 탭마다 프로세스를 분리하고, 웹 서버가 워커 프로세스 모델을 쓰는 이유가 여기 있다. 비용을 더 내고 안정성과 격리를 사는 선택이다.

## 동기화: 공유의 대가

메모리를 공유하는 순간 따라오는 문제다.

### 경쟁 상태와 임계 구역

`counter += 1`은 한 줄이지만 실제로는 **읽기 → 증가 → 쓰기** 세 단계다. 두 스레드가 겹쳐 실행하면 증가가 유실된다.

```text
스레드 A: 읽기(5) ──────────── 쓰기(6)
스레드 B:      읽기(5) ─── 쓰기(6)
결과: 2번 증가했지만 값은 6 (7이어야 함)
```

여러 스레드가 접근하는 공유 자원 구간을 임계 구역이라 하고, 한 번에 하나만 들어가도록 뮤텍스나 세마포어로 보호한다.

| 도구 | 용도 |
| --- | --- |
| 뮤텍스(Mutex) | 한 번에 하나의 스레드만 진입 |
| 세마포어(Semaphore) | 동시에 N개까지 진입 허용 (자원 개수 제한) |
| 조건 변수 | 특정 조건이 될 때까지 대기 |
| 원자적 연산 | 락 없이 단일 연산의 원자성 보장 |

### 데드락의 네 가지 조건

다음 네 조건이 **동시에** 성립할 때만 데드락이 발생한다. 하나만 깨면 예방할 수 있다.

1. **상호 배제**: 자원을 한 번에 하나만 사용할 수 있다.
2. **점유와 대기**: 자원을 쥔 채로 다른 자원을 기다린다.
3. **비선점**: 남이 쥔 자원을 강제로 뺏을 수 없다.
4. **순환 대기**: 대기 관계가 원형을 이룬다.

실무에서 가장 많이 쓰는 예방책은 **락 획득 순서를 전역적으로 통일**해 순환 대기를 없애는 것이다. 타임아웃을 두어 비선점 조건을 깨는 방법도 쓴다.

## 런타임별 구현 차이

같은 "스레드"라도 언어와 런타임에 따라 실제 동작이 다르다.

| 런타임 | 모델 | 유의할 점 |
| --- | --- | --- |
| C/C++ (pthread) | OS 스레드 1:1 | 동기화를 전부 직접 관리 |
| Java | OS 스레드 1:1, Java 21+ 가상 스레드 | 가상 스레드는 I/O 대기에 적합, CPU 작업엔 이득 없음 |
| Go | 고루틴 M:N (런타임 스케줄러) | 작은 스택으로 시작해 수십만 개 생성 가능 |
| Python (CPython) | OS 스레드 1:1 + GIL | 한 번에 하나만 바이트코드 실행 |
| Node.js | 단일 스레드 이벤트 루프 | CPU 작업은 `worker_threads`나 별도 프로세스로 |

특히 Python은 스레드가 OS 스레드인데도 GIL 때문에 순수 Python 계산이 병렬화되지 않는다. 자세한 내용은 [Python GIL과 동시성](../language/2026-07-17-python-gil-concurrency.md)에 정리했다.

### 웹 서버 워커 모델 선택

이 차이는 배포 설정에 그대로 반영된다.

| 모델 | 구조 | 적합한 상황 | 메모리 특성 |
| --- | --- | --- | --- |
| 프로세스(prefork) | 워커 프로세스 N개 | CPU 작업, 안정성 우선 | 워커마다 메모리, CoW로 일부 절약 |
| 스레드 | 프로세스 1개 + 스레드 N개 | 블로킹 I/O 위주 | 스택만 추가되어 가벼움 |
| 이벤트 루프(async) | 스레드 1개 + 논블로킹 I/O | 동시 연결이 매우 많을 때 | 가장 가벼움, 블로킹 호출 금지 |

컨테이너 환경에서는 메모리 한도를 넘기면 OOM Kill이 발생하므로, 워커 수를 정할 때 **워커 1개의 실제 사용량(RSS)을 측정한 뒤 한도로 나누는** 접근이 안전하다. CPU 코어 수만 보고 정하면 메모리에서 터진다.

## 직접 확인해 보기

개념만 읽기보다 실제 값을 보는 편이 이해가 빠르다.

```bash
# 프로세스 목록과 메모리 사용량 (VSZ: 가상, RSS: 실제 물리)
ps -eo pid,tid,comm,vsz,rss --sort=-rss | head

# 특정 프로세스의 스레드 목록
ps -T -p <PID>

# 스레드 개수만 확인 (Linux)
cat /proc/<PID>/status | grep Threads

# 메모리 영역별 매핑 확인 - text, heap, stack이 실제로 보인다
cat /proc/<PID>/maps

# 영역별 상세 사용량 (PSS 포함)
cat /proc/<PID>/smaps

# 요약 형태
pmap -x <PID>
```

macOS에서는 `/proc`이 없으므로 다른 도구를 쓴다.

```bash
vmmap <PID>              # 메모리 영역 확인
ps -M -p <PID>           # 스레드 목록
```

### VSZ와 RSS, 그리고 PSS

메모리 사용량을 볼 때 반드시 구분해야 하는 값이다.

| 지표 | 의미 | 주의점 |
| --- | --- | --- |
| VSZ (가상) | 예약한 가상 주소 공간 전체 | 실제로 쓰지 않는 영역도 포함되어 크게 나온다 |
| RSS (실제) | 물리 메모리에 올라온 크기 | **공유 페이지가 프로세스마다 중복 계산된다** |
| PSS (비례) | 공유 페이지를 공유 프로세스 수로 나눈 값 | 여러 프로세스의 실사용량을 합산할 때 정확하다 |

워커 프로세스 8개의 RSS를 그냥 더하면 실제보다 훨씬 큰 값이 나온다. 공유 라이브러리와 CoW로 공유 중인 페이지가 8번 세어지기 때문이다. 전체 사용량을 추정할 때는 PSS를 봐야 한다.

## 자주 하는 오해

### "스레드가 프로세스보다 항상 빠르다"

생성과 전환 비용은 스레드가 싸다. 하지만 락 경합이 심해지면 스레드가 서로를 기다리느라 오히려 느려질 수 있고, CPython처럼 GIL이 있으면 CPU 작업의 병렬화 자체가 안 된다. 워크로드에 따라 다르므로 측정해야 한다.

### "프로세스를 N개 띄우면 메모리가 N배"

CoW와 공유 라이브러리 덕분에 실제로는 그보다 적다. 다만 참조 카운팅 언어에서는 절약 효과가 줄어든다.

### "스레드 스택 8MB × 스레드 수만큼 메모리를 쓴다"

가상 주소 공간 예약치이고, 실제로 사용한 페이지만 물리 메모리를 차지한다. VSZ와 RSS를 구분해야 한다.

### "지역 변수는 무조건 스레드 안전하다"

변수 자체는 스택에 있어 안전하다. 하지만 지역 변수가 **공유 객체를 가리키는 참조**라면 가리키는 대상은 공유되므로 안전하지 않다.

### "멀티스레드는 멀티코어에서만 의미 있다"

단일 코어에서도 I/O 대기 중에 다른 스레드가 실행되므로 처리량이 올라간다. 병렬성과 동시성은 다른 개념이다.

## 정리

- 프로세스는 독립된 가상 주소 공간을 갖고, 스레드는 그 공간을 공유하며 스택·레지스터·TLS만 따로 갖는다.
- 스레드는 Text, Data, BSS, Heap, 파일 디스크립터를 공유하므로 전역 변수는 위험하고 지역 변수는 안전하다.
- 프로세스 전환은 페이지 테이블을 교체해야 해서 TLB와 캐시 지역성을 잃고, 스레드 전환은 이 비용이 없다.
- `fork()`는 Copy-on-Write로 동작하므로 워커 프로세스의 메모리가 단순히 배수로 늘지 않는다. 단, 참조 카운팅 언어에서는 효과가 줄어든다.
- 스레드는 변수를 직접 공유하고, 프로세스는 IPC를 거친다. 빠른 대신 동기화 책임이 따른다.
- 스레드 하나의 크래시는 프로세스 전체를 죽이지만, 프로세스는 서로 격리된다.
- 메모리 사용량을 합산할 때 RSS는 공유 페이지를 중복 계산하므로 PSS를 봐야 한다.
- 같은 "스레드"라도 GIL, 가상 스레드, 고루틴처럼 런타임마다 동작이 다르므로 확인이 필요하다.
