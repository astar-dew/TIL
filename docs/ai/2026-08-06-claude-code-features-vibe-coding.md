## 학습 목적

Claude Code는 기능이 많아서 목록만 읽으면 오히려 안 쓰게 된다. 중요한 것은 **어떤 상황에서 무엇을 꺼내 쓰는가**다.

이 글에서는 실제로 자주 쓰게 되는 기능을 상황 중심으로 정리하고, 이어서 **AI와 함께 코딩할 때 결과 품질을 좌우하는 원칙**을 정리한다. 도구를 아는 것보다 이쪽이 결과에 더 큰 영향을 준다.

`CLAUDE.md`, Rules, Skills, `settings.json`의 구조는 [Claude Code 기준으로 이해하는 Rules와 Skills](./2026-07-26-claude-code-rules-skills.md)에 따로 정리했으므로 여기서는 짧게만 언급한다.

기준 버전은 2.1.223이다. 기능이 자주 추가되므로 정확한 목록은 `/help`와 `claude --help`로 확인하는 편이 좋다.

## 가장 먼저 이해할 것: 권한 모드

Claude Code를 답답하게 느끼거나 반대로 불안하게 느끼는 이유는 대부분 권한 모드를 모르기 때문이다.

| 모드 | 동작 | 언제 쓰나 |
| --- | --- | --- |
| `manual` | 파일 수정·명령 실행마다 승인 요청 | 익숙하지 않은 저장소, 운영 코드 |
| `acceptEdits` | 파일 편집은 자동 승인, 명령은 확인 | 일반적인 기능 개발 |
| `plan` | **읽기만 가능**. 수정 불가 | 작업 전에 계획부터 세울 때 |
| `auto` | 상황에 따라 자동 판단 | 반복 작업 |
| `dontAsk` | 묻지 않음 | 신뢰하는 범위의 작업 |
| `bypassPermissions` | 모든 검사 우회 | **격리된 샌드박스에서만** |

세션 중에는 `Shift+Tab`으로 모드를 순환할 수 있고, 시작할 때 지정할 수도 있다.

```bash
claude --permission-mode plan
```

`bypassPermissions`는 편하지만 위험하다. 인터넷이 차단된 컨테이너처럼 **되돌릴 수 있는 환경에서만** 쓴다.

### 권한은 설정으로 고정하는 편이 낫다

매번 승인 버튼을 누르는 대신, 안전한 명령은 미리 허용해 두면 흐름이 끊기지 않는다.

```json
{
  "permissions": {
    "allow": ["Bash(git status)", "Bash(npm test)", "Bash(mkdocs build*)"],
    "deny": ["Read(./.env)", "Read(./secrets/**)", "Bash(rm -rf *)"]
  }
}
```

**금지해야 할 것은 지침이 아니라 `deny`로 막는다.** "`.env`는 읽지 마세요"라고 `CLAUDE.md`에 적는 것보다 확실하다.

## 플랜 모드: 가장 저평가된 기능

바로 코드를 고치게 하지 않고 **계획을 먼저 받는** 모드다.

```text
일반 모드   요청 → 바로 파일 수정 → 결과 확인 → 방향이 틀렸으면 되돌리기
플랜 모드   요청 → 탐색과 계획 → 사람이 검토·수정 → 승인 → 실행
```

작업이 클수록 이 차이가 커진다. 방향이 틀린 채로 20개 파일이 수정된 뒤에 알아차리는 것보다, 계획 단계에서 "그건 이미 있는 유틸을 쓰면 된다"고 고쳐주는 편이 훨씬 싸다.

**플랜 모드를 쓰면 좋은 상황**

- 처음 보는 저장소에서 작업할 때
- 여러 파일에 걸친 리팩터링
- "어떻게 구현할지" 자체가 불확실할 때
- 마이그레이션처럼 되돌리기 어려운 작업

**굳이 안 써도 되는 상황**

- 오타 수정, 한 줄 변경
- 이미 방식이 정해진 반복 작업

## 컨텍스트 관리

Claude Code에서 컨텍스트는 **한정된 자원**이다. 대화가 길어지면 오래된 내용이 요약되면서 세부 정보가 흐려진다.

| 명령 | 동작 | 언제 |
| --- | --- | --- |
| `/context` | 지금 무엇이 컨텍스트를 차지하는지 확인 | 느려지거나 이상할 때 |
| `/compact` | 대화를 요약해 압축 | 같은 작업을 계속 이어갈 때 |
| `/clear` | 대화를 완전히 비움 | **다른 작업으로 넘어갈 때** |

가장 자주 하는 실수가 **작업이 바뀌었는데 `/clear`를 하지 않는 것**이다. 앞 작업의 파일과 맥락이 남아 있으면 엉뚱한 파일을 참조하거나 이전 결정에 끌려간다.

```text
로그인 기능 구현 → (완료) → /clear → 결제 API 작업 시작
```

세션을 이어가는 방법도 알아두면 좋다.

```bash
claude -c                  # 이 디렉터리의 마지막 대화 이어가기
claude -r                  # 세션 목록에서 골라 재개
claude -r --fork-session   # 재개하되 새 세션으로 분기 (원본 보존)
```

## 작업 방식을 바꾸는 기능들

### 서브에이전트

별도의 컨텍스트를 가진 에이전트에게 작업을 맡긴다. 핵심 이점은 **컨텍스트 격리**다.

예를 들어 "이 기능이 어디에 구현되어 있는지 찾아줘"를 시키면, 파일을 수십 개 읽는 과정이 메인 대화를 채우지 않고 **결론만 돌아온다.**

- 넓은 범위 탐색
- 독립적인 작업 여러 개를 동시에
- 코드 리뷰처럼 다른 관점이 필요한 작업

### 백그라운드 실행

오래 걸리는 작업을 기다리지 않고 진행할 수 있다.

```bash
claude --bg "테스트 전체 돌리고 실패 목록 정리해줘"
claude agents               # 백그라운드 에이전트 관리
```

세션 안에서도 오래 걸리는 명령을 백그라운드로 돌릴 수 있다. 빌드나 테스트를 돌리면서 다른 파일을 계속 볼 때 유용하다.

### Git worktree로 격리

같은 저장소에서 여러 작업을 병행할 때, 서로 파일을 건드리지 않게 분리한다.

```bash
claude -w feature-login     # 새 worktree에서 세션 시작
```

브랜치를 왔다 갔다 하면서 생기는 충돌을 피할 수 있다.

### 훅 (Hooks)

"매번 X 하고 나면 Y 해줘" 같은 요구는 **부탁이 아니라 훅으로 만들어야** 확실하다. 모델의 판단이 아니라 하네스가 실행하기 때문이다.

| 이벤트 | 쓰임새 |
| --- | --- |
| `PreToolUse` | 위험한 명령 차단, 사전 검증 |
| `PostToolUse` | 파일 수정 후 포맷터·린터 자동 실행 |
| `UserPromptSubmit` | 프롬프트마다 컨텍스트 주입 |
| `Stop` | 작업 완료 알림 |
| `SessionStart` | 세션 시작 시 환경 준비 |

"파일을 고칠 때마다 prettier를 돌려주세요"를 지침으로 적으면 가끔 빠뜨리지만, `PostToolUse` 훅으로 만들면 항상 실행된다.

### MCP

외부 서비스를 도구로 연결하는 표준이다. GitHub, 데이터베이스, 사내 API 등을 붙이면 Claude가 직접 조회할 수 있다.

```bash
claude mcp        # MCP 서버 관리
```

### 되돌리기

작업이 잘못된 방향으로 갔을 때 이전 시점으로 되돌릴 수 있다. `Esc`로 진행 중인 작업을 중단하고, 되돌리기 기능으로 파일 상태를 이전으로 복구한다.

다만 **Git 커밋만큼 확실하지는 않다.** 중요한 작업 전에는 커밋해 두는 습관이 여전히 더 안전하다.

## 입력할 때 알아두면 편한 것들

| 입력 | 동작 |
| --- | --- |
| `@경로/파일` | 파일을 컨텍스트에 직접 넣기 |
| `!명령어` | 셸 명령을 바로 실행하고 결과를 대화에 남기기 |
| `#내용` | 메모리에 바로 추가 |
| 이미지 붙여넣기 | 스크린샷, 에러 화면, 디자인 시안 전달 |
| `Esc` | 진행 중인 작업 중단 |

`!` 는 특히 유용하다. 대화형 로그인처럼 사람이 직접 쳐야 하는 명령의 결과를 바로 공유할 수 있다.

```text
! gh auth status
```

## 모델과 사고 강도

```bash
claude --model opus         # 모델 선택 (opus, sonnet, fable 등)
claude --effort high        # 사고 강도 (low, medium, high, xhigh, max)
```

| 상황 | 권장 |
| --- | --- |
| 단순 반복, 파일 정리 | 가벼운 모델 + 낮은 effort |
| 일반 기능 개발 | 기본값 |
| 아키텍처 설계, 어려운 버그 | 높은 모델 + 높은 effort |

무조건 최대치로 두는 것이 답은 아니다. 간단한 작업까지 오래 생각하면 비용과 대기 시간만 늘어난다.

## 자동화와 헤드리스 실행

대화 없이 스크립트처럼 쓸 수 있다.

```bash
# 결과만 출력
claude -p "이 저장소의 테스트 커버리지를 요약해줘"

# JSON으로 받아 파이프라인에 연결
claude -p "변경된 파일 목록을 정리해줘" --output-format json

# 구조를 강제
claude -p "PR 요약" --json-schema '{"type":"object","properties":{"title":{"type":"string"}},"required":["title"]}'

# 비용 상한
claude -p "리팩터링 후보 찾기" --max-budget-usd 2
```

CI에서 쓸 때는 `--max-budget-usd`로 상한을 두고, `--allowedTools`로 도구를 제한하는 편이 안전하다.

설정이 꼬였을 때 원인을 좁히는 명령도 알아두면 좋다.

```bash
claude doctor        # 설치 상태 점검
claude --safe-mode   # 모든 커스터마이징을 끄고 실행
```

`--safe-mode`로 정상 동작하면 문제는 `CLAUDE.md`, 훅, MCP, 플러그인 중 하나다.

## 바이브 코딩을 잘하기 위한 원칙

기능보다 이쪽이 결과에 훨씬 큰 영향을 준다.

### 1. 검증 수단을 먼저 만든다

가장 중요한 원칙이다. AI가 **스스로 결과를 확인할 수 있는 수단**이 있으면 품질이 급격히 올라간다.

```text
검증 수단이 없을 때   코드 작성 → "아마 될 겁니다" → 사람이 직접 확인
검증 수단이 있을 때   코드 작성 → 테스트 실행 → 실패 확인 → 수정 → 통과
```

테스트, 타입 검사, 린터, 빌드 명령 중 하나라도 있으면 스스로 고칠 수 있다. 새 프로젝트를 시작할 때 테스트 환경부터 갖추는 것이 결과적으로 가장 빠른 길이다.

이 저장소에서 `mkdocs build --strict`를 검증에 쓰는 것도 같은 이유다. 링크가 깨지면 빌드가 실패하므로 잘못된 문서가 배포되지 않는다.

### 2. 컨텍스트를 정확히 준다

가장 흔한 실패 원인은 모델의 능력이 아니라 **정보 부족**이다.

```text
나쁨: "로그인이 안 돼요"

좋음: "로그인 API에서 401이 납니다.
      - 파일: src/auth/login.ts
      - 에러: JsonWebTokenError: invalid signature
      - 재현: POST /api/login에 올바른 계정으로 요청
      - 최근 변경: 어제 JWT 라이브러리를 v9로 올렸습니다"
```

에러 메시지는 요약하지 말고 **전문을 그대로** 붙여넣는 것이 좋다. 사람이 보기에 중요해 보이지 않는 줄에 원인이 있는 경우가 많다.

### 3. 큰 작업은 쪼갠다

"관리자 페이지 전체 만들어줘"보다 "관리자 레이아웃 → 사용자 목록 → 필터 → 수정 폼" 순으로 나누는 편이 낫다.

- 중간에 방향을 고칠 수 있다
- 각 단계에서 검증할 수 있다
- 컨텍스트가 덜 소모된다
- 문제가 생겼을 때 원인 범위가 좁다

### 4. 자주 커밋한다

AI와 작업할 때 커밋은 **저장 지점**이다. 잘 동작하는 상태를 커밋해 두면 과감하게 시도해 볼 수 있다.

```bash
git add -A && git commit -m "wip: 로그인 폼까지 동작 확인"
```

되돌릴 수 있다는 확신이 있으면 더 큰 변경을 맡길 수 있다.

### 5. 반복되는 지시는 설정으로 옮긴다

같은 말을 세 번 하고 있다면 그건 프롬프트가 아니라 **설정으로 갈 내용**이다.

| 반복하는 말 | 옮길 곳 |
| --- | --- |
| "한국어로 답해주세요" | `CLAUDE.md` |
| "이 폴더에서는 이 규칙을 지켜주세요" | 경로별 Rule |
| "글 쓸 때 이 순서로 해주세요" | Skill |
| "수정 후엔 포맷터 돌려주세요" | Hook |
| "이 명령은 승인 없이 실행해도 돼요" | `permissions.allow` |

이렇게 환경을 다듬어 가는 과정을 하네스 엔지니어링이라고 부른다. 프롬프트를 길게 쓰는 것보다 효과가 오래 간다.

### 6. 추측을 사실처럼 말하지 않게 한다

`CLAUDE.md`에 한 줄 넣어두면 체감 차이가 크다.

```md
- 확인하지 않은 내용은 사실처럼 단정하지 않는다.
- 라이브러리 사용법은 실제 코드나 공식 문서를 확인한 뒤 답한다.
- 모르면 모른다고 답한다.
```

### 7. 결과를 읽는다

가장 지키기 어려운 원칙이다. 잘 동작하는 것처럼 보이면 diff를 안 보게 되는데, 이때 다음이 슬쩍 들어온다.

- 필요 없는 의존성 추가
- 기존 유틸을 두고 비슷한 함수를 새로 만듦
- 에러 처리를 `try/catch`로 삼켜서 문제를 감춤
- 테스트를 통과시키려고 단언을 약화

**"동작하는가"와 "이 코드가 맞는가"는 다른 질문**이다.

### 8. 실패하면 프롬프트가 아니라 환경을 고친다

같은 실수가 반복되면 프롬프트를 더 길게 쓰는 대신 원인을 본다.

```text
증상: 자꾸 잘못된 폴더에 파일을 만든다
→ 프롬프트에 매번 경로를 적기 (임시방편)
→ CLAUDE.md에 디렉터리 구조를 적기 (근본 해결)

증상: 커밋 메시지 형식이 제각각이다
→ 매번 지적하기
→ Rule이나 Skill로 형식을 정의하기
```

### 9. 컨텍스트 위생을 지킨다

- 작업이 바뀌면 `/clear`
- 관련 없는 파일을 잔뜩 열게 하지 않기
- 긴 로그는 필요한 부분만 붙여넣기
- 탐색은 서브에이전트에 맡겨 메인 컨텍스트를 아끼기

### 10. 위험한 작업은 권한으로 막는다

지침은 확률적이지만 `deny`는 확정적이다. 운영 DB 접근, `.env` 읽기, 강제 푸시처럼 **사고가 나면 되돌리기 어려운 것**은 설정으로 막는다.

## 안티패턴

### 한 번에 너무 많이 요청하기

"전체 리팩터링해줘"는 검토 불가능한 결과를 만든다.

### 오래된 대화를 계속 이어가기

컨텍스트가 요약되면서 초반 요구사항이 흐려진다. 작업이 끝나면 정리한다.

### 승인 없이 전부 자동 실행

편하지만 잘못된 방향으로 멀리 가버린다. 최소한 계획 단계에서는 사람이 개입하는 편이 낫다.

### 검증 없이 "됐다"로 넘기기

테스트도 안 돌리고 커밋하면 문제가 나중에 몰려서 터진다.

### `CLAUDE.md`를 너무 길게 쓰기

지침이 많아지면 개별 항목이 잘 지켜지지 않는다. 핵심만 남기고 나머지는 경로별 Rule과 Skill로 분리한다.

### 이미 있는 기능을 모르고 새로 만들게 하기

먼저 "비슷한 기능이 이미 있는지 찾아봐 달라"고 요청하면 중복 구현을 줄일 수 있다.

## 정리

- 권한 모드를 먼저 이해해야 도구가 답답하지도 위험하지도 않게 쓸 수 있다.
- 큰 작업은 플랜 모드로 계획을 먼저 검토하면 방향 오류의 비용이 크게 줄어든다.
- 컨텍스트는 자원이다. 작업이 바뀌면 `/clear`, 이어갈 때는 `/compact`를 쓴다.
- 서브에이전트는 탐색 과정을 메인 대화에서 격리해 컨텍스트를 아낀다.
- "매번 해야 하는 일"은 지침이 아니라 훅으로 만들어야 확실하다.
- 결과 품질을 가장 크게 좌우하는 것은 **AI가 스스로 검증할 수 있는 수단의 유무**다.
- 에러는 요약하지 말고 전문을 준다. 정보 부족이 가장 흔한 실패 원인이다.
- 자주 커밋해서 되돌릴 수 있는 상태를 유지하면 더 과감하게 맡길 수 있다.
- 반복되는 지시는 `CLAUDE.md`, Rule, Skill, Hook, 권한 설정으로 옮긴다.
- "동작하는가"와 "이 코드가 맞는가"는 다른 질문이므로 diff는 직접 읽는다.
